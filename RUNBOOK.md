## 0. Перед стартом (один раз)

```bash
# API-ключ уже в .env — проверить, что он актуальный:
grep OPENAI_API_KEY .env

# Приватный датасет — НЕ копировать поверх agentic-bank-public/, класть рядом
# и указывать --data-dir явно на каждой команде ниже. Например:
#   /path/to/private-dataset/  (со своими documents/, master_ledger_2025.csv, submission_template.json)
```

**Модель — решение принято заранее (см. обоснование в конце файла): по умолчанию `dev` (mini) для основного прогона.** `COVENANT_AGENT_PROFILE` не задан в `.env` → пайплайн уже по умолчанию идёт на `dev`, ничего включать не нужно. Если сознательно переключаетесь на топ-тир — только после того, как рабочий submission на mini уже есть на диске (см. решение по модели ниже).

## 1. Ingestion — сначала, отдельно, ПЕРЕД тратой токенов

```bash
python scripts/run_ingestion.py --data-dir /path/to/private-dataset -v \
    --report cache/private_ingestion.json
```

Смотрите на exit code и вывод. Если увидели:

```
AccountLinkingRiskError: N/M required scenarios have NO current credit_agreement document...
```

**СТОП. Не запускайте extraction/calculation.** Это значит формат `account_id` в приватных данных, скорее всего, не "ACC-<цифры>" — до сдачи всё равно надо чинить `resolution/accounts.py`'s `ACCOUNT_TOKEN_RE`, но если побежать дальше — все ячейки уйдут в одинаковый fallback-COMPLIANT, а бюджет на API сгорит впустую. Вручную откройте пару строк леджера и пару документов, посмотрите как реально называются счета, только потом чините regex и перезапускайте ingestion.

Если ingestion прошёл чисто (`AccountLinkingRiskError` не сработал, у каждого сценария есть `credit_agreement`) — переходите дальше.

## 2. Полный расчёт (extraction + linking + calculation в одном вызове)

```bash
python scripts/run_calculation.py --data-dir /path/to/private-dataset -v \
    --report cache/private_results.json \
    --facts-cache cache/private_facts.json
```

`--facts-cache` пишется по ходу, по одному сценарию за раз — так что прогресс не теряется технически. **Но если процесс прервался ДО конца, повторный запуск с той же `--facts-cache` НЕ доэкстрактит недостающие сценарии** — файл уже существует, скрипт просто загружает то, что в нём есть, и молча идёт дальше (недостающие сценарии получат fallback с причиной `"no covenant clauses extracted for this scenario (missing credit agreement or extraction failure)"`, без явной ошибки о прерывании). Если прервалось на середине — либо (а) удалите/переименуйте `cache/private_facts.json` и запустите заново с нуля, либо (б) посмотрите в выводе, каких сценариев не хватает, и добейте их по одному через `--scenario <id> --report cache/scenario_X.json` (не через `--facts-cache`, у него свой путь извлечения), потом вручную объедините JSON-файлы перед `build_submission.py`.

Подтверждено живым прогоном (2026-08-09, оба полных 27-сценарийных прогона — dev и final): `extract_all_facts` реально ловит исключение на уровне отдельного сценария (не всего батча) и продолжает остальные — при обоих прогонах результат был "27/27 scenario(s) ok", прерываний не было ни разу.

Следите за консолью на:
- `[OTHER-TYPE: generic catch-all, verify manually]` — ковенант новой, невиданной формы, посчитан "как есть", стоит вручную проверить эту ячейку глазами.
- `[FALLBACK: ...]` — сколько ячеек ушло в fallback и почему.

## 3. Собрать финальный submission.json

```bash
python scripts/build_submission.py \
    --results cache/private_results.json \
    --template /path/to/private-dataset/submission_template.json \
    --team "ВАШЕ_НАЗВАНИЕ_КОМАНДЫ" \
    --contact-email "ВАШ_EMAIL" \
    --model "gpt-5.4-mini (dev profile)" \
    --output submission.json
```

**Exit code 0 = готово к сдаче. Exit code 1 = где-то null-ячейки, читайте вывод, что именно недосчиталось, и почините перед отправкой** (сообщение прямо назовёт `scenario.covenant`).

Скрипт сам перечитывает записанный файл и проверяет структуру — если exit 0 и нет warning про missing cells, файл структурно готов.

## Если что-то не так

| Симптом | Что делать |
|---|---|
| `AccountLinkingRiskError` при ingestion | См. шаг 1 — не продолжать, проверить формат `account_id` вручную |
| Скрипт падает с traceback на середине пакетного прогона | `--scenario <id>` чтобы перезапустить только упавший сценарий (не тратить бюджет на остальных 11) |
| `build_submission.py` вернул exit 1 | Прочитать список missing cells в выводе, дозапустить `run_calculation.py --scenario <id>` для недостающих, повторить сборку |
| Не уверены, что цифры разумные | `--ground-truth` работает только на публичном датасете (self-score) — на приватном такой проверки нет, полагайтесь на `[OTHER-TYPE]`/`[FALLBACK]` пометки и здравый смысл по паре ячеек вручную |

## Решение по модели — что было запланировано и что реально произошло

**Первоначальный план (принят заранее, до появления приватного датасета):** держать основной прогон на `dev` (mini), топ-тир-бюджет (лимит друга, ~250k advisory, не hard API limit — см. `llm_client.py`'s `TOP_TIER_TOKEN_BUDGET`) не трогать вслепую, пробовать `final` только точечно на 1 сценарии после того, как `dev`-submission уже готов. Обоснование тогда: полный 12-сценарийный `dev`-прогон на публичных данных потратил 362,908 токенов, из них 261,758 в двух бюджетных call-типах (covenant_extraction + transaction_categorization) — уже больше лимита друга на одном прогоне.

**Что реально произошло (2026-08-09, приватный датасет, 27 сценариев):** по явному, осознанному решению (не героический фикс, а прямая инструкция) план был пересмотрен — бюджет 250k осознанно превышен. Оба профиля прогнаны ПОЛНОСТЬЮ на всех 27 сценариях:

| Прогон | Токенов всего | Из них топ-тир (`gpt-5.4`) | Результат |
|---|---|---|---|
| `dev` (mini) | 917,065 | 0 | `submission_dev.json`, 27/27 extraction+linking ok |
| `final` (top-tier) | 925,958 | 601,489 | `submission_final.json`, 27/27 extraction+linking ok |

Оба прогона завершились без прерываний (ни разу не потребовалось восстановление через `--scenario <id>`). Реальный измеренный расход на сценарий для топ-тира (~22,528 токенов на 2 бюджетных call-типа) оказался близок к `dev`'s собственному (~21,813) — токеномика топ-тира не оказалась катастрофически дороже в токенах, ограничение именно в размере самого бюджета (250k), а не в неожиданном взрыве расхода на сценарий.

**Итог:** три submission-файла на диске (`submission_dev.json`, `submission_final.json`, `submission_hybrid.json` — точечный ручной override 4 ячеек по итогам read-only диагностики 12 status-disagreement ячеек). Подробности сравнения — README, раздел "Multiple submission attempts". Ни один файл не затирает другой; выбор порядка отправки (какой попыткой №1/№2/№3) — решение человека, не автоматизировано.
